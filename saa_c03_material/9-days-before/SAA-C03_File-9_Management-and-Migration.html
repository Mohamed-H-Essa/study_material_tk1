01 Observability — logs, metrics & the audit trail

Three services, three questions they answer

The exam's favorite confusion lives here. CloudWatch asks "how is it performing?", CloudTrail asks "who did what?", and Config asks "what is the configuration now, and was it ever non-compliant?" Get those three sentences right and a whole class of questions falls over.

CloudWatch — metrics, alarms, logs

CloudWatch collects metrics (CPU, network, custom), fires alarms on thresholds, stores Logs, and lets you query them with Logs Insights. The catch the exam loves: the hypervisor cannot see inside the OS, so memory and disk usage are NOT default metrics — you install the CloudWatch agent to push them. A composite alarm combines several alarms with AND/OR logic so you alert on a real condition instead of a single noisy signal.

Key fact — memory needs the agent

Any stem that says "alert on memory utilization" or "track disk space inside the instance" is pointing at the CloudWatch agent (or a custom metric). EC2's built-in metrics stop at the hypervisor boundary: CPU, network, disk I/O — but never RAM or filesystem free space. Picking "use the default EC2 memory metric" is the trap, because it does not exist.

EventBridge vs CloudWatch Events

EventBridge is the evolution of CloudWatch Events — same event bus, broader reach (SaaS partners, custom buses, schema registry). For the exam treat them as the same engine: an event pattern or schedule matches an event and routes it to a target (Lambda, SQS, SNS, Step Functions). "Run something on a cron schedule" or "react to an AWS API event" → an EventBridge rule.

CloudTrail — the audit log

CloudTrail records API calls. Management events (control-plane: RunInstances, CreateBucket) are on by default; data events (S3 object-level GetObject/PutObject, Lambda invokes) are high-volume and opt-in. A multi-region trail captures every Region into one place; log file integrity validation produces a hash digest so you can prove logs weren't tampered with — the compliance answer.

AWS Config — configuration state & compliance

Config records the configuration history of resources, evaluates them against rules (managed or custom), flags non-compliant resources, and can auto-remediate via SSM Automation. "Continuously check that no security group allows 0.0.0.0/0 on 22, and fix it" is a Config rule + remediation, not CloudTrail.

Classic trap — track config changes vs record API calls

The single most reused observability question: "track configuration changes on resources AND record a history of API calls." The answer is Config for the config changes, CloudTrail for the API calls. Swap them and you've picked the trap. CloudWatch never "records API calls" — it watches performance. If you see CloudWatch offered as the API-history tool, it's bait.

// field note — the digest that proves nothing was touched

When auditors ask "can you prove these logs weren't edited," CloudTrail's log file integrity validation is the receipt. Every hour CloudTrail writes a digest file to S3 containing SHA-256 hashes of the log files for that period, and the digest itself is signed. Change one byte of a delivered log and the hash no longer matches — tamper-evident by design. It's the kind of feature you never think about until a compliance question hinges on it, and then it's the only right answer.

02 Governance & operations at scale

Run a hundred accounts like one

Once you have more than a couple of accounts, the exam expects you to govern centrally: Organizations for the boundary, Control Tower for the guardrails, Systems Manager for the day-to-day, CloudFormation for the blueprint.

AWS Organizations & Control Tower

Organizations groups accounts into OUs, gives you consolidated billing (one bill, shared volume discounts and Reserved/Savings pooling), and enforces Service Control Policies (SCPs). Control Tower sits on top: it sets up a landing zone (multi-account baseline) and applies guardrails — preventive (SCPs) and detective (Config rules) — from a dashboard.

Key fact — what an SCP actually does

An SCP sets the maximum permissions for accounts in an OU — it's a guardrail, not a grant. It never gives access; an action is allowed only if both the SCP and an IAM policy permit it. SCPs don't apply to the management (payer) account, and they don't touch service-linked roles. "Centrally prevent any account from leaving a Region / disabling CloudTrail / using a banned service" → SCP.

SCP behaviorReality
Grants permissions?No — only restricts. You still need IAM allow.

Systems Manager (SSM) — the operations toolbox

  • Session Manager — shell access to instances with no SSH, no bastion, no open inbound ports, no key pairs. Needs the SSM agent + an instance role. The "secure access, least overhead" answer.
  • Patch Manager — define patch baselines and maintenance windows; automate OS/app patching across the fleet.
  • Run Command — execute a command/script across many instances at once, on demand, no SSH.
  • State Manager — keep instances in a defined state (config drift correction).
  • Parameter Store — config & secrets (SecureString via KMS); free standard tier. Secrets Manager adds managed rotation.

Classic trap — Session Manager vs Run Command vs Patch Manager

They sound interchangeable but the verbs differ. Interactive shell into one box without SSH → Session Manager. Run a script across many boxes once → Run Command. Keep them patched on a schedule → Patch Manager. A stem saying "patch all instances regularly" that offers "use Session Manager to patch" is the bait — Session Manager connects, it doesn't orchestrate patching.

CloudFormation — infrastructure as code

A template creates a stack. StackSets deploy the same stack across many accounts and Regions in one operation. Change sets preview what an update will do before you apply it. Drift detection finds resources changed outside CloudFormation. Nested stacks compose reusable components within one stack.

FeatureUse it when…
StackSetsOne template deployed to multiple accounts and/or Regions centrally (often from the Organizations management account).
Nested stacksBreak one large stack into reusable child templates within a single account/stack.
Change setsPreview the impact of an update before executing it.
Drift detectionDetect manual changes that diverged from the template.

Other governance reflexes: Service Catalog lets a central team publish approved, pre-configured products (CloudFormation-backed) that users self-serve within guardrails — "let developers launch only approved configurations." Trusted Advisor checks across five pillars (cost optimization, performance, security, fault tolerance, service limits). AWS Health Dashboard tells you about events affecting your resources. Elastic Beanstalk is the PaaS option: hand it code, it provisions and manages the EC2/ASG/ELB stack for you — "deploy a web app with the least operational effort and full control of the underlying resources."

// field note — the guardrail that saves the bill

A favorite real-world Organizations pattern: a single SCP on the root OU denying every Region except the two you operate in. New accounts inherit it automatically, so a developer who fat-fingers a launch into ap-south-1 simply can't — the API is denied before any resource exists. No CloudWatch alarm, no nightly cleanup Lambda, no surprise cross-Region data-transfer charges. One preventive guardrail beats a dozen detective ones, which is exactly the instinct the "least operational overhead" clause rewards.

03 Migration & data transfer

Match the workload to the mover

Almost every migration question is really a matching exercise: a database wants DMS, whole servers want MGN, online files want DataSync, and petabytes with no bandwidth want Snow. Learn the four tells and the rest is detail.

The 7 Rs, in one breath

Retire, Retain, Rehost (lift-and-shift), Relocate (e.g. VMware), Repurchase (move to SaaS), Replatform (lift-tinker-shift, e.g. to RDS), Refactor (re-architect for cloud-native). The exam mostly cares about Rehost (→ MGN) and Replatform (→ managed DB via DMS).

The four movers

ToolMovesTell
AWS DMSDatabases (live, with minimal downtime via CDC)"migrate the database", "keep source online during migration", "ongoing replication"
MGN (Application Migration Service)Whole servers / VMs — lift-and-shift"rehost", "migrate physical/VMware servers as-is", "no code changes"
DataSyncFile/object data online over the network"NFS/SMB to S3/EFS/FSx", "you have bandwidth", "scheduled/recurring transfer"
Snow FamilyBulk data offline (physical device)"petabytes", "limited/no bandwidth", "weeks over the wire is too slow"

Key fact — DMS homogeneous vs heterogeneous

Same engine to same engine (Oracle→Oracle on RDS, MySQL→Aurora MySQL) is homogeneous — DMS alone. Different engine (Oracle→Aurora PostgreSQL, SQL Server→MySQL) is heterogeneous and needs the Schema Conversion Tool (SCT) first to convert schema/code, then DMS to move the data. "Convert the schema then migrate" with a different target engine is the two-step SCT + DMS answer.

The supporting cast

  • Migration Hub — single pane to track migration progress across tools and accounts (discovery + status), not a mover itself.
  • Transfer Family — fully managed SFTP/FTPS/FTP endpoint that lands files straight into S3/EFS. "Partners upload via SFTP, minimal ops" → Transfer Family, not an EC2 SFTP server.
  • Snowball Edge (Storage / Compute Optimized), Snowcone (smallest, rugged), and the retired Snowmobile — choose by data size and edge-compute needs.
  • DataSync + DMS combo — DataSync for the bulk initial file copy, DMS CDC for ongoing DB sync, when both data types move together.

Classic trap — DataSync vs Snowball on bandwidth

The deciding factor is almost always time-over-the-wire. Do the arithmetic the exam implies: many petabytes on a constrained link would take months → Snowball Edge (ship it). Tens of terabytes with a healthy connection, or a recurring sync → DataSync. A stem that stresses "limited bandwidth / would take too long online" is steering you to Snow; one that stresses "ongoing / scheduled / over Direct Connect" is steering you to DataSync.

// field note — a truck full of disks

AWS once shipped Snowmobile: a 45-foot shipping container towed by a semi-truck, holding up to 100 PB, for customers moving entire data centers or exabyte archives. The physics is the punchline of an old networking adage — "never underestimate the bandwidth of a truck full of tapes hurtling down the highway." When a transfer would take a year online, the fastest network on Earth is a vehicle. Snowmobile has since been retired, but the Snow family lives on for the same reason: past a certain scale, offline beats online.
