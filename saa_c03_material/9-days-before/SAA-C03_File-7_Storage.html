01 Amazon S3 — classes, lifecycle & controls

The same bytes, seven prices — pick by how you'll touch them

S3 questions are almost never "store the file." They're "store it for this access pattern, this retrieval SLA, this retention rule, at the lowest cost." Get the access pattern and the answer falls out.

The storage classes, ranked by how often you read

All classes (except One Zone) store across ≥3 AZs and share the famous eleven nines (99.999999999%) of durability. What changes is availability, retrieval latency, minimum billable duration, and per-GB price.

ClassUse whenRetrievalMin duration / AZs

Key fact — Intelligent-Tiering vs Lifecycle

If the stem says access patterns are unknown, changing, or unpredictable → S3 Intelligent-Tiering (it moves objects between tiers automatically, no retrieval fees). If the stem says known age-based pattern ("after 30 days it's rarely read, after 1 year archive it") → write an S3 Lifecycle rule. Both can coexist. The word "unknown" is the tell for Intelligent-Tiering; a clock/age is the tell for Lifecycle.

Lifecycle, versioning, replication

Lifecycle rules do two things: transition objects to cheaper classes on a schedule, and expire (delete) them — including cleaning up noncurrent versions and incomplete multipart uploads. Versioning keeps every overwrite/delete (a delete just adds a delete marker), and is the prerequisite for replication and MFA Delete (requires the root user + MFA token to permanently delete versions). Replication is async and needs versioning on both ends: CRR (cross-Region — DR, latency, compliance) vs SRR (same-Region — log aggregation, prod→test). Add S3 Replication Time Control (RTC) for a 15-minute replication SLA.

Access, edge & protection

  • Pre-signed URLs grant time-limited access to a private object using the signer's permissions — the canonical "let users upload/download without making the bucket public" answer.
  • Transfer Acceleration speeds long-distance uploads via CloudFront edge locations; multipart upload parallelizes large objects (use it >100 MB, required >5 GB).
  • Object Lock (WORM): Governance mode = special permission can override; Compliance mode = nobody, not even root, can delete until retention expires. Needs versioning.
  • Block Public Access is on by default at account + bucket level — the backstop against accidental public buckets.
  • Storage Lens gives org-wide usage/activity analytics and cost-optimization recommendations; S3 encryption is on by default (SSE-S3 / AES-256) for all new objects.

Classic trap — One Zone-IA durability

One Zone-IA still has eleven nines of durability within its single AZ, but if that AZ is destroyed the data is gone — it isn't replicated across AZs. So it's only correct when the data is easily re-created (thumbnails, secondary copies, processed derivatives). Any stem with "must not lose," "irreplaceable," or "compliance" + One Zone-IA is bait.

// field note — the bucket that ate the headlines

For years the most common AWS breach wasn't a hacker — it was a misconfigured S3 bucket left public. So many leaks (voter records, telecom logs, defense contractor files) traced to one wrong toggle that in 2018 AWS shipped Block Public Access and later turned it on by default for new buckets, plus painted public buckets bright orange in the console. The exam echoes this: when a stem says "prevent accidental public exposure across the whole account," the answer is Block Public Access, not a hand-written bucket policy.

02 Block & file storage — EBS, instance store, EFS, FSx

Block, file, or object — the question answers itself once you spot the protocol

One instance, one volume → EBS. Many Linux instances, one shared POSIX mount → EFS. Windows/SMB, HPC, or a specific filesystem feature → FSx. Throwaway scratch on the host → instance store.

EBS volume types (recap + extend)

TypeClassPick it forCeiling
gp3SSDdefault boot/general; IOPS & throughput priced independently of size16,000 IOPS / 1,000 MiB/s
gp2SSDlegacy general; IOPS scale with size (3/GB)16,000 IOPS
io1 / io2SSDhigh sustained IOPS, low latency; io2 = 99.999% durability64,000 IOPS
io2 Block ExpressSSDhighest IOPS/throughput, sub-ms; large DBs (SAP HANA, Oracle)256,000 IOPS
st1HDDbig sequential throughput (logs, big data); can't boot500 MiB/s
sc1HDDcoldest, cheapest, infrequent sequential; can't boot250 MiB/s

EBS levers: snapshots are incremental and stored in S3; Fast Snapshot Restore (FSR) removes first-touch latency; Multi-Attach lets one io1/io2 volume attach to up to 16 Nitro instances in the same AZ (clustered apps only); volumes are AZ-locked; encryption (KMS) and resize/type-change happen live with elastic volumes.

Key fact — EBS vs EFS vs instance store

EBS = one volume, one instance, single AZ, block. Instance store = physically attached NVMe, fastest, but ephemeral — data dies on stop/terminate (great for cache/scratch/buffers). EFS = managed NFS, multi-AZ regional, mounts on thousands of Linux instances at once, grows automatically. When a stem says "shared across many instances and concurrently writable," EBS is wrong (Multi-Attach aside) — it's EFS.

The FSx family — match the tell

FSx flavorProtocolStem tell
Windows File ServerSMBWindows apps, Active Directory integration, NTFS ACLs, DFS
LustreLustre/POSIXHPC, ML training, hundreds of GB/s, links to an S3 data set
NetApp ONTAPNFS, SMB, iSCSImigrating NetApp, multi-protocol, snapshots/dedup/cloning
OpenZFSNFSmoving from on-prem ZFS, low-latency NFS, snapshots

Classic trap — EFS is Linux-only

EFS speaks NFS, so it serves Linux. The moment a stem mentions Windows instances needing a shared file share, EFS is wrong — reach for FSx for Windows File Server (SMB). And "HPC / Lustre / parallel access to S3 training data" is never EFS either; that's FSx for Lustre.

// field note — the EBS that wasn't there

In the April 2011 EBS outage in us-east-1, a network change triggered a storm of EBS volumes frantically trying to re-mirror themselves, exhausting capacity and taking down a chunk of the internet (Reddit, Quora, Foursquare) for days. The architectural lesson the exam still tests: EBS is a single-AZ service. Snapshots live in S3 and span the Region, but the live volume does not — true resilience means snapshots, multi-AZ designs, or a regional file system like EFS.

03 Hybrid & data movement — Gateway, DataSync, Transfer, Snow, Backup

Getting data on and off AWS without melting the network link

Two axes decide everything: is this an ongoing sync or a one-time bulk move, and do you have bandwidth or not. Online + ongoing → DataSync / Gateway. Offline + huge → Snow.

Storage Gateway — keep on-prem apps, back them with AWS

GatewayOn-prem seesUse when
S3 File GatewayNFS/SMB sharefile access on-prem, objects land in S3
Volume — CachediSCSI blockprimary data in S3, hot data cached locally (low local footprint)
Volume — StorediSCSI blockprimary data kept on-prem, async backup to S3 (low-latency local reads)
Tape Gateway (VTL)virtual tape libraryreplace physical tape backups → Glacier

Movers

  • DataSync — online, agent-based, fast incremental transfer between on-prem (NFS/SMB/HDFS) and AWS (S3/EFS/FSx); handles scheduling, encryption, validation. The default for "ongoing or one-time online migration with bandwidth."
  • AWS Transfer Family — fully managed SFTP/FTPS/FTP endpoint in front of S3/EFS; for partners who only speak those protocols.
  • AWS Backup — one place to schedule, run, and govern backups (with Backup Vault Lock for WORM) across EBS, EFS, RDS, DynamoDB, FSx, Storage Gateway, EC2 and more.

Snow family — offline bulk by size + connectivity

DeviceCapacityReach for it when
Snowcone~8–14 TBsmall, rugged, portable; edge/IoT; can ship or DataSync
Snowball Edge~80 TB usableTBs–low PBs; Storage or Compute optimized (edge compute)
Snowmobileup to 100 PBexabyte-scale data-center evacuations (a literal truck)

Key fact — the bandwidth math

The exam wants you to notice when the wire is too slow. Rough rule: shipping a Snowball beats the network when moving large data sets over a constrained link in a deadline. If a stem gives you "X TB, Y Mbps link, must finish in Z days," do the napkin math — if online transfer blows the deadline, the answer is Snow. If bandwidth is fine and it's recurring, it's DataSync.

Classic trap — File Gateway vs DataSync

Both touch S3, but they solve different problems. DataSync = move/copy data from A to B (a migration or scheduled sync job). S3 File Gateway = give on-prem apps an ongoing NFS/SMB mount whose files persist as S3 objects (a permanent access layer, with local caching). "Migrate then decommission" → DataSync. "On-prem apps keep using a file share long-term, backed by S3" → File Gateway.

// field note — the truck is real

AWS Snowmobile debuted at re:Invent 2016 as a 45-foot shipping container on a semi-truck holding up to 100 PB, driven to your data center with an armed escort. The point wasn't theater: at exabyte scale, the fastest network connection on earth still loses to physically moving disks. It's the literal embodiment of "never underestimate the bandwidth of a truck full of hard drives." (AWS has since retired Snowmobile, but the principle — and the exam answer for the largest migrations — endures in the Snow family.)
