01 Identity & access management, deep

Deny beats allow, and nobody should hold a long-lived key

IAM is the spine of the whole domain. The exam tests how policies combine across accounts, who can do what, and the two reflexes it rewards every time: least privilege, and temporary credentials over static keys.

The four building blocks

Users are long-lived humans/apps (avoid where possible). Groups attach policies to many users at once — groups can't be nested and aren't principals. Roles are the hero of the exam: an identity with no permanent credentials that anyone trusted (an EC2 instance, a Lambda, another account, a federated user) assumes to get temporary credentials via STS. Policies are JSON documents granting/denying actions.

How a request is actually evaluated

For every API call AWS gathers all applicable policies and applies this order: an explicit Deny anywhere wins, always. Otherwise, the action must be explicitly Allowed by something; the default is an implicit deny. So the mental model is: explicit deny > explicit allow > implicit deny. SCPs, permission boundaries, identity policies and resource policies all feed into this — and any one of them denying is fatal.

Key fact — identity policy vs resource policy

An identity-based policy hangs off a user/group/role and says "this principal can do X." A resource-based policy hangs off the resource (an S3 bucket policy, an SQS queue policy, a KMS key policy) and says "these principals can touch me." Cross-account access is the resource-policy's home turf: the resource grants the external account, and that account's IAM also allows the action — both locks must open.

The org-level guardrails

Classic trap — SCP vs permission boundary on an OU

When the requirement is "enforce a rule across every account in the org (or an OU), so that even the root user obeys it," the answer is an SCP attached to the OU — not a permission boundary. Permission boundaries cap a single user/role and can't be attached to an OU at all. An SCP that denies ec2:CreateVolume when ec2:Encrypted is false is a real exam answer; the same idea phrased as a permission boundary on the OU is the bait.

Cross-account & instance reflexes: EC2 gets permissions through an instance profile (a wrapper around a role) — never store access keys on the box. To use another account, you sts:AssumeRole a role there that trusts you; STS hands back short-lived creds. External/web identities (Google, SAML corporate IdP) reach AWS through federation, again landing on a role. The recurring right answer to "stop using long-lived keys" is: use a role.

// field note — the keys in the GitHub repo

The most common way AWS accounts get drained isn't a clever exploit — it's an access key committed to a public Git repo. Bots scrape GitHub within seconds; people have woken to five-figure crypto-mining bills from a key pushed minutes earlier. AWS now scans public repos and auto-quarantines leaked keys, but the architectural lesson is the exam's favorite reflex: roles and temporary credentials can't be committed to a repo because they don't exist until they're assumed. Every "minimize credential management / no long-lived keys" question is pointing at this.

02 Data protection & encryption

Who holds the key decides the answer

Nearly every encryption question reduces to one axis: how much of the key lifecycle does AWS manage, and how much do you. Get the SSE family and the KMS-vs-CloudHSM line straight and these become free points.

KMS & envelope encryption

KMS manages symmetric/asymmetric keys backed by FIPS-validated HSMs, with a key policy (a resource policy) as the root of access control. Keys come two ways: AWS-managed (auto-created per service, e.g. aws/s3, you can't edit the policy or control rotation) and customer-managed (CMK) — you control the key policy, grants, and rotation (automatic annual rotation is a checkbox on CMKs). KMS does envelope encryption: it encrypts a per-object data key with the master key, so KMS never has to encrypt your gigabytes directly — the service encrypts data with the plaintext data key and stores the wrapped key alongside.

Key fact — KMS vs CloudHSM

KMS is multi-tenant, fully managed, FIPS 140-2 Level 3 validated, and integrates with everything — the default for "encrypt at rest with least effort." CloudHSM is a single-tenant, dedicated hardware appliance you control entirely, also FIPS 140-2 Level 3, for when you must hold the keys yourself, run your own PKI, or satisfy a regulation that forbids a shared service. You can even back a KMS custom key store with CloudHSM to get KMS integration plus dedicated hardware.

Classic trap — Secrets Manager vs Parameter Store

Both store secrets encrypted with KMS. The deciding word is rotation: Secrets Manager has built-in automatic rotation (and Lambda hooks for DB credentials, plus cross-Region replication) — pick it when the stem says "rotate credentials automatically." SSM Parameter Store is free for standard parameters and great for config/plaintext or SecureString values, but it has no native rotation. "Minimize operational overhead of credential rotation" → Secrets Manager; "store config cheaply" → Parameter Store.

Where encryption shows up everywhere else: EBS, RDS, EFS, and S3 all do at-rest encryption with KMS keys (RDS encryption must be set at creation — you can't encrypt an existing unencrypted DB in place; you snapshot, copy-with-encryption, restore). ACM issues and auto-renews free public TLS certs for in-transit encryption on ALB/CloudFront/API Gateway (ACM public certs don't attach to EC2 directly). In transit = TLS; at rest = KMS.

// field note — encrypt the snapshot, not the disk

Engineers routinely get stuck trying to "turn on encryption" for a running, unencrypted RDS instance or EBS volume — there's no toggle, and the support forums are full of the discovery. The real path is the copy trick: snapshot → copy the snapshot with encryption enabled (choosing a KMS key) → restore from the encrypted copy. It's a one-time migration, not a setting, and it's exactly the kind of "which sequence of steps" the exam likes to test.

03 Edge protection & the detective stack

Block at the edge, then watch everything

Two clusters live here. The preventive edge — WAF, Shield, firewalls — and the detective stack — GuardDuty, Inspector, Macie, Config, Security Hub. The exam tests "which one finds X," and they're easy to confuse.

The edge: WAF, Shield, firewalls

WAF filters HTTP/S at Layer 7 with managed rule groups (OWASP, bot control, SQL-injection) and rate-based rules; it attaches to CloudFront, ALB, API Gateway, AppSync — never an NLB or EC2 directly. Shield Standard is free, automatic L3/L4 DDoS protection for everyone; Shield Advanced adds L7 protection, a 24/7 response team, and cost-protection for scaling during an attack. Network Firewall is a managed, stateful VPC-level firewall (filters all traffic in/out of a VPC, not just HTTP) — the VPC-wide complement to WAF's app-layer focus. Firewall Manager centrally manages WAF/Shield/Network Firewall/security-group rules across all accounts in an Organization.

Key fact — the detective trio

Three "find the bad thing" services the exam loves to swap: GuardDuty = intelligent threat detection from logs (VPC Flow, DNS, CloudTrail) — "is someone attacking / is an instance compromised / crypto-mining." Inspector = automated vulnerability scanning of EC2, ECR images and Lambda for CVEs and unintended network exposure. Macie = ML that finds sensitive data / PII sitting in S3. Threat → GuardDuty, CVE → Inspector, PII-in-S3 → Macie.

Classic trap — Config vs CloudTrail vs GuardDuty

They sound similar but answer different questions. CloudTrail = who did what (API call audit log). Config = what does my resource look like and is it compliant (configuration state + rules over time). GuardDuty = is the activity malicious (threat intelligence on the logs). "Detect a security group that was opened to 0.0.0.0/0 and flag non-compliance" → Config rule. "Detect that the open port is being exploited by a known-bad IP" → GuardDuty.

// field note — Capital One and the metadata door

In 2019 a misconfigured WAF on Capital One's infrastructure was tricked into making requests to the EC2 instance metadata endpoint, handing an attacker the instance role's temporary credentials, which were then used to read ~100 million customer records from S3. The breach is the canonical case for several exam reflexes at once: least-privilege roles (the role had broad S3 read), GuardDuty would flag the anomalous S3 access, Macie would have flagged the unprotected PII, and IMDSv2 closes the metadata door. One misconfiguration, the entire detective stack as the lesson.
