01 VPC fundamentals — subnets, routing & the two firewalls

A VPC is a routing table and two firewalls in a trench coat

Almost every VPC question reduces to three things: does this subnet have a route to the internet, does the security group allow the request, and does the NACL allow the reply. Get those three reflexes and most of the domain falls over.

CIDR, subnets, and what "public" actually means

You give a VPC a CIDR block (e.g. 10.0.0.0/16 = 65,536 addresses) and carve subnets from it. AWS reserves 5 addresses per subnet (first four + last), so a /24 gives you 251 usable, not 256. A subnet is public only if its route table sends 0.0.0.0/0 to an Internet Gateway (IGW) and the instance has a public/Elastic IP. Drop either and it's private. Subnets are AZ-scoped — one subnet lives in exactly one AZ, which is why HA designs need a subnet per AZ.

Getting out without getting in: NAT

Instances in a private subnet often need outbound internet (patches, API calls) but must accept no inbound from the internet. That's a NAT Gateway: it lives in a public subnet, and the private subnet's route table points 0.0.0.0/0 at it. For IPv6 the equivalent is an egress-only Internet Gateway (IPv6 addresses are public by default, so the EIGW gives outbound-only without the inbound).

Key fact — one NAT Gateway per AZ

A NAT Gateway is HA inside its own AZ only. If you run a single NAT Gateway and route all three AZs' private subnets through it, you've created a cross-AZ dependency and a SPOF: lose that AZ and every private subnet loses internet. The exam-correct HA pattern is one NAT Gateway per AZ, each AZ's private route table pointing at its own. (Bonus: it also kills the cross-AZ data-transfer charge.)

The two firewalls — and why this is the #1 networking trap

ScopePer-ENI / instancePer-subnet

Classic trap — stateless means ephemeral ports

Because NACLs are stateless, allowing inbound HTTPS (443) is not enough — the server's reply leaves on a high ephemeral port, so the outbound NACL must allow 1024–65535 (clients use ~32768–65535 on Linux). Symptom: requests arrive but responses never come back, and the SG looks fine. The other trap: "block a single malicious IP" — a security group can't deny, so the answer is always a NACL deny rule.

// field note — the default that bites

When you create a brand-new custom NACL, it starts with an implicit deny on everything inbound and outbound — so attaching it to a working subnet instantly black-holes all traffic until you add explicit allow rules. The default NACL that ships with every new VPC is the opposite: it allows everything, which is why most people never think about NACLs at all… right up until a security team replaces the default with a locked-down custom one and the app mysteriously can't get its replies back. That single asymmetry — default NACL = allow-all, custom NACL = deny-all — accounts for a surprising share of "it worked yesterday" VPC tickets.

02 Connecting VPCs & reaching on-prem

How two clouds — or a cloud and a data center — touch

The exam loves the moment your two-VPC peering design hits its tenth VPC, or your "we have Direct Connect" answer forgets DX isn't encrypted. Match the connectivity to the scale and the requirement.

Key fact — peering is non-transitive

If VPC A peers with B, and B peers with C, A still cannot reach C through B — peering carries no transit. Full any-to-any connectivity with peering needs a full mesh (n·(n−1)/2 connections), which is why "dozens/hundreds of VPCs" or "centrally managed connectivity" is the tell to switch to a Transit Gateway hub. Peering also forbids overlapping CIDR blocks on both ends.

Direct Connect, deeper than File 1

A DX connection is a physical cross-connect at an AWS Direct Connect location. It carries logical virtual interfaces (VIFs): a private VIF reaches your VPC's private IPs (via a Virtual Private Gateway or Direct Connect Gateway), a public VIF reaches AWS public endpoints (S3, DynamoDB) over the dedicated line, and a transit VIF connects to a Transit Gateway. A Direct Connect Gateway lets one DX connection reach VPCs in multiple Regions. Connections come dedicated (a whole port from AWS, 1/10/100 Gbps) or hosted (a slice from a partner, finer sub-1G speeds).

Classic trap — Direct Connect is private, not encrypted

DX gives you a private dedicated line, but the data on it is not encrypted. When a stem adds "all data in transit must be encrypted," the answer is a Site-to-Site VPN running over the Direct Connect link (private VIF + IPsec) — private path and encryption, with consistent latency. There is no "encryption" checkbox on a DX connection.

// field note — why Transit Gateway exists

Before TGW launched in late 2018, large AWS customers building 50+ VPCs faced a brutal choice: a full mesh of peering connections (which grows quadratically — 50 VPCs is 1,225 peerings to manage), or a self-built "transit VPC" running EC2 routers that you had to size, patch, and pay for around the clock. Transit Gateway collapsed all of it into a single managed hub: every VPC and every VPN/DX attachment connects once, routing is transitive, and route tables on the gateway control who can talk to whom. The quadratic-mesh pain is exactly the scenario the exam dramatizes when it says "hundreds of VPCs across many accounts."

03 Endpoints, DNS & flow visibility

Reach AWS services without ever touching the internet

The single most repeated networking distinction on the exam: gateway endpoint vs interface endpoint. Then hybrid DNS and flow logs — the two things that make a private design observable and resolvable.

The endpoint coin-flip you must never lose

Gateway endpointInterface endpoint (PrivateLink)
Works forOnly S3 and DynamoDBAlmost every other AWS service + your own/partner services
HowA route-table entry (prefix list) to the serviceAn ENI with a private IP in your subnet
CostFreeHourly per-AZ charge + per-GB data
Cross-VPC / on-premNo (route table only)Yes — reachable over peering, VPN, DX

Key fact — "S3 or DynamoDB and free" → gateway

If a private-subnet instance must call S3 or DynamoDB with no internet path and no extra cost, the answer is a gateway endpoint — a route-table entry, nothing billed. For any other service (SQS, KMS, Secrets Manager, EC2 API, SSM…) or to reach the endpoint from on-prem/another VPC, you need an interface endpoint (PrivateLink), which is an ENI and carries an hourly + data charge.

Hybrid DNS — Route 53 Resolver endpoints

By default a VPC resolves names via the Route 53 Resolver (the .2 address). To bridge DNS with a data center you add Resolver endpoints:

  • Outbound endpoint + forwarding rules: VPC resolvers forward queries for on-prem domains (e.g. corp.example.com) out to your on-prem DNS servers.
  • Inbound endpoint: on-prem DNS servers forward queries in to AWS so they can resolve private hosted zone records and AWS resources.
  • Private hosted zone: a Route 53 zone resolvable only inside associated VPCs — internal names that never touch public DNS.

Classic trap — Flow Logs don't capture payloads

VPC Flow Logs record IP traffic metadata — source/dest IP, ports, protocol, bytes, ACCEPT/REJECT — to CloudWatch Logs or S3. They are the go-to for "who connected to what / why is this traffic being rejected." But they do not capture packet contents. If a stem needs payload inspection, that's VPC Traffic Mirroring, not Flow Logs. And a REJECT in a flow log is your cue to check the SG (allow missing) or the NACL (deny rule or missing ephemeral-port allow).

// field note — the free endpoint that pays for itself

A gateway endpoint for S3 is free, but its real value shows up on the bill in a different column. Without it, a private-subnet fleet pulling terabytes from S3 routes every byte through a NAT Gateway — and NAT Gateway data-processing charges (per-GB) on heavy S3 traffic can dwarf almost everything else in a VPC's networking spend. Adding the gateway endpoint sends that S3 traffic straight out via the route table, bypassing NAT entirely. It's one of the few "more secure and cheaper" changes in AWS, which is exactly why the exam keeps offering it as the least-effort, lowest-cost answer.
