01 Serverless analytics & query

Your data already lives in S3 — query it where it sits

The reflex the exam rewards over and over: when the data is sitting in S3 and someone wants to "run SQL," "build a dashboard," or "generate a report" with the LEAST operational effort, you almost never spin up a cluster. You point a serverless engine at the bucket.

Athena — serverless SQL on S3

Amazon Athena runs standard SQL directly against files in S3 with zero infrastructure. There's no cluster to size, patch, or pay for when idle — you pay per terabyte scanned. That pricing model is the whole exam game: convert raw CSV/JSON to columnar Parquet/ORC, compress, and partition by date/region so a query touches a fraction of the data. Less scanned = cheaper and faster. Athena reads its table definitions from the Glue Data Catalog.

Glue — serverless ETL & the Data Catalog

AWS Glue is serverless extract-transform-load on managed Spark. Its two exam-critical pieces: crawlers scan your data, infer schema, and populate the Data Catalog (the central metadata store Athena, EMR, and Redshift Spectrum all read); and ETL jobs transform/convert data (e.g. JSON → Parquet) with no servers to run. "LEAST operational overhead" + "transform data / discover schema" = Glue, not a hand-built Spark cluster.

Key fact — the data-lake reflex

The default serverless analytics stack on the exam is S3 (data lake) → Glue crawler/ETL (catalog + transform to Parquet) → Athena (SQL) → QuickSight (dashboards). Every box in that chain is serverless and pay-per-use. When a stem says "consolidate data into one place, run one-time queries, show KPIs, least overhead," that pipeline is the answer — reach for a cluster (Redshift/EMR) only when the stem forces you to.

QuickSight — the BI layer

Amazon QuickSight is the managed business-intelligence / dashboard service. It connects to Athena, S3, Redshift, RDS and more, and its in-memory engine SPICE caches data for fast interactive dashboards. When the requirement is "visualize," "dashboard," "KPIs," or "share reports with business users," that's QuickSight — not Athena (which only returns query results) and not OpenSearch (which is search/log analytics).

The streaming-to-store layer: Firehose vs Data Streams vs Data Analytics

You met Kinesis Data Streams in File 2 as a stream-vs-queue concept (warm). Here it's about the loading side:

ServiceWhat it isStem tell
Kinesis Data FirehoseFully-managed delivery stream. No shards, no consumers to code. Auto-loads to S3, Redshift, OpenSearch, Splunk; can buffer, compress, convert to Parquet, and invoke Lambda to transform en route."deliver / load streaming data to S3/Redshift/OpenSearch", "near-real-time", "least management"
Kinesis Data StreamsReal-time stream you read with your own consumers; shards, ordering, replay, sub-second. You manage scaling/consumers."custom real-time processing", "multiple consumers replay the same data", "millisecond"
Kinesis Data AnalyticsRun SQL (or Apache Flink) on the stream in flight — windowed aggregations, real-time metrics."analyze / transform the streaming data with SQL as it arrives"

Classic trap — Firehose is not real-time-for-consumers

Firehose is the least-effort way to LAND streaming data in a store, but it buffers (seconds–minutes) and you don't write consumer code against it. If a stem needs sub-second delivery to custom consumers, or multiple independent apps to replay the same records, that's Data Streams, not Firehose. And if it needs no destination at all — just "process records yourself" — Firehose, which exists only to deliver, is wrong.

// field note — pay for what you scan

Athena's pay-per-scan model has a famous failure mode: teams point it at terabytes of raw JSON and watch the bill climb per query. AWS's own guidance is blunt — converting a dataset to compressed, columnar Parquet and partitioning it routinely cuts both cost and runtime by 30–90%, because Athena reads only the columns and partitions a query needs. The lesson the exam keeps testing: the cheapest analytics tool is still expensive if you let it read everything.

02 Big data clusters & search

When serverless isn't the answer — clusters, governance & search

Athena and Glue cover most "query the lake" questions, but the exam keeps a handful of services for when the stem forces a cluster, a governance layer, or full-text search. Knowing exactly when each one beats the serverless default is the whole skill.

EMR — managed Hadoop / Spark

Amazon EMR runs managed Hadoop, Spark, Hive, Presto, HBase on a cluster you size. Reach for it when the stem demands heavy, custom big-data frameworks, petabyte-scale batch processing, existing Hadoop/Spark code to migrate, or fine control over the engine — things Athena's pure-SQL serverless model can't do. For cost, EMR runs beautifully on Spot for task nodes and as a transient cluster (spin up, run the job, terminate). If a stem just says "run SQL on S3 occasionally, least effort," EMR is the over-engineered distractor; Athena wins.

PickWhenPay model
AthenaAd-hoc / one-time SQL on S3, no infra to run, least effortper TB scanned
EMRCustom Spark/Hadoop frameworks, huge batch ETL, migrate existing Hadoop, ML pipelinesper cluster-hour (Spot-friendly)
RedshiftPetabyte-scale data warehouse, complex joins, frequent BI on structured data, consistent perfper provisioned (or serverless) capacity

Lake Formation — governance for the lake

AWS Lake Formation sits on top of S3 + Glue and adds centralized, fine-grained permissions — table-, column-, and row-level access for analysts across Athena, Redshift Spectrum, and EMR, managed in one place instead of juggling S3 bucket policies and IAM. Exam tell: "data lake" + "fine-grained / column-level access control" + "least administrative effort" → Lake Formation.

OpenSearch — log analytics & search

Amazon OpenSearch Service (formerly Elasticsearch Service) is for full-text search and log/operational analytics with near-real-time dashboards (OpenSearch Dashboards / Kibana). The signature pipeline: logs → Kinesis Data Firehose → OpenSearch → dashboards. When a stem wants to search/index documents or interactively analyze and visualize log streams, it's OpenSearch — not Athena (batch SQL) and not QuickSight (BI on structured sources).

Redshift recap + Spectrum + RA3

Redshift basics were File 3 (warm). Two exam add-ons: Redshift Spectrum lets a Redshift cluster query data directly in S3 without loading it — join warm warehouse tables to cold S3 history. RA3 nodes separate compute from storage (scale them independently; managed S3-backed storage), and AQUA is a hardware-accelerated cache layer. MSK (Managed Streaming for Apache Kafka) is the pick when the stem explicitly says Kafka or "migrate an existing Kafka workload"; otherwise Kinesis is the AWS-native streaming default.

Classic trap — OpenSearch vs QuickSight vs Athena

Three "analytics" services, three different jobs. Athena = serverless SQL queries (you get rows back). QuickSight = BI dashboards for business KPIs on structured data. OpenSearch = full-text search + interactive log analytics. A stem about searching documents or live-troubleshooting log streams that pairs "QuickSight" is bait; one about business KPI dashboards that pairs "OpenSearch" is also bait.

// field note — the rename nobody forgets

In 2021, after a licensing dispute with Elastic, AWS forked Elasticsearch and renamed its managed service Amazon OpenSearch Service. SAA-C03 questions still write it as "Amazon OpenSearch Service (Amazon Elasticsearch Service)" so candidates who learned the old name aren't tripped up. If you see either name, treat them as the same service — search and log analytics.

03 API & application integration front door

The managed front door to your serverless backend

The other half of this domain: standing up a managed, scalable, secured entry point for clients — and wiring the integration glue (fan-out, queues, orchestration) behind it. You've met the glue in File 2; here it joins the front door.

API Gateway — three API flavors

TypeReach for it when…Note
REST APIFull feature set: API keys + usage plans, request/response transforms, caching, WAF, fine-grained throttling, edge-optimizedmost features, higher cost per call
HTTP APISimpler, cheaper, lower-latency proxy to Lambda / HTTP backends; JWT auth built in~70% cheaper; fewer features (no usage plans/caching)
WebSocket APITwo-way, stateful connections — chat, live feeds, push notificationsserver can push to clients

Endpoints, throttling & caching

Endpoint types: Edge-optimized (default, fronted by CloudFront for global clients), Regional (clients in-Region, or you bring your own CloudFront), Private (only reachable from inside a VPC via an interface endpoint). API Gateway has built-in throttling (account + per-method limits) to protect the backend from spikes, and caching on REST APIs to cut backend calls and latency.

Auth & rate-limiting clients

  • Cognito user pool authorizer — managed user sign-in/JWT validation with zero auth code. Least effort when the stem already uses Cognito.
  • Lambda authorizer — custom auth logic (validate a third-party token, call an external IdP) when Cognito doesn't fit.
  • IAM authorization — SigV4 for internal AWS callers.
  • API keys + usage plans — identify callers and enforce rate / quota per client (e.g. throttle a tier of users). For blocking malicious traffic, pair with AWS WAF.

Key fact — the canonical serverless API

API Gateway → Lambda → DynamoDB is the exam's default fully-managed, auto-scaling, no-servers-to-patch web backend. When a stem wants a REST/HTTP API with the least operational overhead and unpredictable traffic, this is the stack. Add a Cognito user pool authorizer for managed user auth, usage plans to rate-limit clients, and WAF to filter malicious requests.

AppSync — managed GraphQL

AWS AppSync is managed GraphQL: clients fetch exactly the fields they need in one request, with built-in real-time subscriptions and offline sync — ideal for mobile/web apps aggregating multiple data sources (DynamoDB, RDS, Lambda, OpenSearch). Exam tell: the word GraphQL, or "mobile app needs real-time updates and to combine several backends in one query." If it just says "REST API," that's API Gateway.

The integration glue — recap as a win

Behind the front door sit the File 2 services: SNS (pub/sub fan-out to many subscribers), SQS (durable decoupling buffer), EventBridge (event bus + routing rules + scheduling), and Step Functions (visual orchestration of multi-step / long-running workflows with retries and state). The exam loves API Gateway publishing straight to SNS/SQS (no Lambda needed) and Step Functions coordinating a sequence of Lambdas.

Classic trap — usage plans vs WAF vs authorizers

Three controls that all "protect the API," each with a distinct job. Usage plans + API keys = rate/quota limiting per client. WAF = block malicious patterns / bad IPs / SQLi. Authorizers (Cognito/Lambda) = verify who the caller is. A stem about throttling abusive-but-valid callers wants usage plans; one about filtering attack traffic wants WAF; one about validating logged-in users wants a Cognito authorizer. Mixing them up is a classic distractor.

// field note — the API throttle that saved the launch

API Gateway's default account throttle (10,000 req/s, 5,000 burst) exists for one reason teams learn the hard way: a sudden traffic spike — a viral post, a misbehaving client in a retry loop — can stampede an unprotected Lambda+DynamoDB backend into throttling and cascading failures. The exam's lesson lands cleanly: the front door's job isn't only routing, it's protecting the backend, so "spiky/unpredictable traffic" stems reward API Gateway throttling and caching over a raw load balancer.
